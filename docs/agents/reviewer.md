# Reviewer contract

A reviewer agent reads a **read-only** snapshot and posts structured findings. It does not
edit the repository, write the store or receive the daemon token.

## Input

A job bundle contains the prompt, the snapshot diff, the schema, metadata and the protocol
versions. The reviewer should treat all of it as read-only data, except its own report.

The snapshot has a file manifest, hunks, optional content and warnings. Findings must point
at paths and lines that exist in the snapshot; a finding anchored outside it is rejected.

## Report

A minimal `schemaVersion: 1` report:

```json
{
  "schemaVersion": 1,
  "summary": "One blocking issue in retry handling.",
  "riskLevel": "high",
  "findings": [
    {
      "id": "f1",
      "severity": "blocker",
      "category": "correctness",
      "confidence": "high",
      "kind": "issue",
      "file": "src/app.ts",
      "lineStart": 42,
      "lineEnd": 42,
      "title": "Last item is dropped on retry",
      "rationale": "The loop exits before the final item is flushed.",
      "evidence": "The early return skips the flush branch.",
      "suggestion": {
        "original": "return items;",
        "replacement": "items.push(last); return items;"
      }
    }
  ],
  "questions": [],
  "tests": { "ran": false, "commands": [] },
  "verification": []
}
```

Rules:

- `report.findings` is canonical; do not return a conflicting result-level copy.
- `riskLevel`, `findings`, `questions`, `tests` and `verification` are part of the report; findings use `file`, not `path`.
- Severity values are the schema's enum, not free text.
- Text fields are capped at 32 KiB.
- A suggestion whose `original` does not match after whitespace normalization is dropped
  and the finding is marked `unanchored`.
- Invalid findings are rejected individually; a structurally invalid report is
  `invalid-output`.

## Coverage and effort

The reviewer should report what it actually inspected. A coverage ledger makes partial
review explicit; do not present a partial pass as complete. Questions and findings are not
capped, but the job's effort budget and shard manifest bound the work.

A `none` backend records a skipped report; a command backend runs an argv array without a
shell. A worker timeout is recorded as a retryable `agent/failed` event.

## Read-only guard

The DSH worker allows only:

- `read`
- `grep`
- `glob`
- `review_status`
- `review_feedback`

Shell, write, network, delegation and review-mutating tools fail closed even if a preset
exposes them. The reviewer must not be given the daemon token through the prompt or the
harness environment.

## Worker loop

If you are implementing the transport half, use
[`@sir_yami/reviewd-worker`](../reference/worker-protocol.md). The loop:

1. registers with `POST /api/workers/register`;
2. long-polls `GET /api/jobs/next`;
3. runs the harness with the lease prompt and cwd;
4. posts findings and a report with the lease `attemptId`;
5. posts a retryable or non-retryable failure when the run fails;
6. heartbeats to extend the 60-second lease.

Duplicate posts with the same `attemptId` are no-ops. A stale registration triggers one
re-registration.

## Verification

Before treating a review as done:

- the report belongs to the latest round;
- the reviewer is done (`done`, `partial`, `skipped` or `failed` is explicit);
- coverage is complete if a coverage ledger is present;
- accepted/dismissed findings are human decisions, not reviewer claims;
- the feedback package is regenerated by submit, not by the reviewer.

See [Reviewer findings in the HTTP API](../reference/http-api.md#jobs-and-workers) and the
[worker protocol](../reference/worker-protocol.md).
